# Migrating from RapidRepo 8.x to 9.0

RapidRepo 9.0 splits the library into a provider-neutral core and an EF Core provider, so that other persistence technologies can implement the same contracts. Application code that depends only on `IRepository<TEntity, TKey>` and `IUnitOfWork<TUserKey>` keeps working with any provider.

Most upgrades are mechanical: add one package, rename one DI call, and rewrite the read calls that passed EF-specific arguments. The 8.x repository and unit of work class names still compile, with an obsolete warning, so your class declarations do not have to change on day one.

---

## 1. Packages

| 8.x | 9.0 |
|---|---|
| `RapidRepo` (EF Core implementation included) | `RapidRepo` (provider-neutral core, no EF Core dependency) **plus** `RapidRepo.EntityFrameworkCore` |
| `RapidRepo.Extensions.DependencyInjection` | Unchanged name; now provider-neutral |
| `RapidRepo.SourceGenerators` | Unchanged name |

```bash
dotnet add package RapidRepo.EntityFrameworkCore
```

`RapidRepo.EntityFrameworkCore` depends on `RapidRepo` and `RapidRepo.Extensions.DependencyInjection`, so it is the only package an EF Core application has to add.

---

## 2. Dependency injection

| 8.x | 9.0 |
|---|---|
| `options.UseDbContext<AppDbContext>()` | `options.UseEntityFrameworkCore<AppDbContext>()` |
| `options.ThrowOnMissingDbContext = true` | `options.UseEntityFrameworkCore(ef => ef.ThrowOnMissingDbContext = true)` |
| `RegisterGenericRepositories = true` without `UseDbContext` | Add `options.UseEntityFrameworkCore()`. Without a provider this now throws instead of silently registering EF's repository |
| Scanning EF repositories without `UseDbContext` | Add `options.UseEntityFrameworkCore()`, so that `IEfRepository<,>` is treated as a root interface |

```csharp
builder.Services.AddRapidRepo(options =>
{
    options.UseEntityFrameworkCore<AppDbContext>();   // was UseDbContext<AppDbContext>()
    options.ScanAssembliesContaining<ProductRepository>();
    options.RegisterGenericRepositories = true;
    options.UseUnitOfWork<AppUnitOfWork>();
});
```

`UseEntityFrameworkCore` lives in the `Microsoft.Extensions.DependencyInjection` namespace, like `AddRapidRepo`, so no new `using` is needed.

---

## 3. Repository and unit of work classes

The 8.x names are kept as obsolete subclasses of the new ones. They report warning `RRMIG001` and will be removed in RapidRepo 10.0.

| 8.x | 9.0 |
|---|---|
| `BaseRepository<TEntity, TId>` | `EfRepository<TEntity, TId>` |
| `Repository<TEntity, TId>` | `EfRepository<TEntity, TId>` |
| `Repository<TEntity, TId, TContext>` | `EfRepository<TEntity, TId, TContext>` |
| `ReadOnlyRepository<TEntity, TId>` | `EfReadOnlyRepository<TEntity, TId>` |
| `WriteRepository<TEntity, TId>` | `EfWriteRepository<TEntity, TId>` |
| `BaseWriteRepository<TEntity, TId>` | `EfRepository<TEntity, TId>`, or derive from `EfWriteRepository<TEntity, TId>` |
| `UnitOfWork<TUserKey>` | `EfUnitOfWork<TUserKey>` |

The new types are in the `RapidRepo.EntityFrameworkCore` namespace:

```csharp
using RapidRepo.EntityFrameworkCore;

public class ProductRepository(AppDbContext db) : EfRepository<Product, long>(db), IProductRepository;

public class AppUnitOfWork(AppDbContext db) : EfUnitOfWork<Guid>(db, Guid.Empty), IAppUnitOfWork;
```

To silence the warnings while you migrate, add `<NoWarn>$(NoWarn);RRMIG001</NoWarn>` to the project.

In custom repositories, `DbContext` is now a protected property rather than a protected field. Reading it is unchanged; code that passed it by `ref` or `out` no longer compiles.

`SupportsSoftDelete` is now a protected static property rather than a protected instance field. Reading it by its bare name is unchanged; `this.SupportsSoftDelete` and `base.SupportsSoftDelete` no longer compile, so drop the qualifier.

In custom units of work, `DbContext` is now get-only. In 8.x it had a protected setter; it is set once by the constructor now, also on the obsolete `UnitOfWork<TUserKey>`. Pass the context to the constructor instead of assigning it later.

### The unit of work no longer disposes the `DbContext`

In 8.x, `UnitOfWork.Dispose()` disposed a `DbContext` it did not own, typically one the DI container had created. `EfUnitOfWork` never disposes the context and no longer implements `IDisposable`; whoever created the context disposes it.

- The obsolete `UnitOfWork<TUserKey>` keeps an empty `Dispose()`, so a unit of work interface declared as `IAppUnitOfWork : IUnitOfWork<Guid>, IDisposable` still compiles.
- Once you move to `EfUnitOfWork<TUserKey>`, remove `IDisposable` from the interface, or implement `Dispose()` yourself.

## 4. Read calls

The read contract no longer exposes EF Core types. The EF-specific parameters moved into an options object, and sorting is declarative.

| 8.x | 9.0 |
|---|---|
| `orderBy: q => q.OrderBy(p => p.Name)` | `orderBy: SortOrder<Product>.By(p => p.Name)` |
| `orderBy: q => q.OrderBy(p => p.A).ThenByDescending(p => p.B)` | `SortOrder<Product>.By(p => p.A).ThenByDescending(p => p.B)` |
| `include: q => q.Include(p => p.Category)` | `options: new EfReadOptions<Product> { Include = q => q.Include(p => p.Category) }` |
| `track: false` | `options: new EfReadOptions<Product> { Track = false }` |
| `useSplitQueries: true` | `options: new EfReadOptions<Product> { SplitQuery = true }` |
| `ignoreQueryFilters: true` (to see soft-deleted rows) | `options: new ReadOptions { IncludeDeleted = true }` |
| `ignoreQueryFilters: true` (to bypass every filter) | `options: new EfReadOptions<Product> { IgnoreAllQueryFilters = true }` |
| An ordering `SortOrder` cannot express | `options: new EfReadOptions<Product> { OrderBy = q => ... }` |
| `GetAllPaged(cond, orderBy, include, split, filters, track, pageIndex, pageSize)` | `GetAllPaged(cond, orderBy, pageIndex, pageSize, options)` |
| `GetSingle*(cond, orderBy, ...)` | `GetSingle*(cond, options)`. The sort order is gone: it could not change which single row matches |

```csharp
// 8.x
var products = await repo.GetAllAsync(
    condition: p => p.IsActive,
    orderBy: q => q.OrderBy(p => p.Name),
    include: q => q.Include(p => p.Category),
    track: false);

// 9.0
var products = await repo.GetAllAsync(
    condition: p => p.IsActive,
    orderBy: SortOrder<Product>.By(p => p.Name),
    options: new EfReadOptions<Product> { Include = q => q.Include(p => p.Category), Track = false });
```

`ReadOptions` and `SortOrder<T>` are in the `RapidRepo.Repositories` namespace, and `EfReadOptions<T>` is in `RapidRepo.EntityFrameworkCore`.

### Projections that also take a condition must return a reference type

`GetFirst*`, `GetSingle*` and `GetAll` projections now require `TResult : class`. Without that constraint, `GetFirstOrDefault(p => p.IsActive)` would be ambiguous between a condition and a `bool` projection. Project scalars through an anonymous type or a record:

```csharp
// 8.x
IEnumerable<string> names = repo.GetAll(selector: p => p.Name);   // still fine: string is a class
IEnumerable<int> ids = repo.GetAll(selector: p => p.Id);          // no longer compiles

// 9.0
var ids = repo.GetAll(selector: p => new { p.Id }).Select(x => x.Id);
```

`GetById` and `GetByIds` projections are unaffected and may still return scalars.

### Test doubles

Mocks, stubs and fakes of `IReadOnlyRepository<,>` or `IRepository<,>` follow the new signatures too. A Moq setup that matched the 8.x parameters, for example `It.IsAny<Func<IQueryable<Product>, IOrderedQueryable<Product>>>()` for `orderBy` or the `include`, `track` and `ignoreQueryFilters` arguments, no longer compiles:

```csharp
// 8.x
repo.Setup(r => r.GetAllAsync(
    It.IsAny<Expression<Func<Product, bool>>>(),
    It.IsAny<Func<IQueryable<Product>, IOrderedQueryable<Product>>>(),
    It.IsAny<Func<IQueryable<Product>, IIncludableQueryable<Product, object>>>(),
    It.IsAny<bool>(), It.IsAny<bool>(), It.IsAny<bool>(),
    It.IsAny<CancellationToken>()));

// 9.0
repo.Setup(r => r.GetAllAsync(
    It.IsAny<Expression<Func<Product, bool>>>(),
    It.IsAny<SortOrder<Product>>(),
    It.IsAny<ReadOptions>(),
    It.IsAny<CancellationToken>()));
```

### Hand-written queries in custom repositories

`BuildQuery(condition, orderBy, include, useSplitQueries, ignoreQueryFilters, track)` is now `BuildQuery(condition, orderBy, options)`. For free-form LINQ, call `Query(options)`, which every `EfRepository` subclass has and which returns an `IQueryable<TEntity>`. Derive your repository interface from `IEfRepository<TEntity, TKey>` only if callers outside the repository need it too:

```csharp
public async Task<List<ProductSummary>> SearchAsync(string term, int limit)
    => await Query(new EfReadOptions<Product> { Track = false })
        .Where(p => p.Name.Contains(term))
        .OrderByDescending(p => p.CreatedAt)
        .Select(p => new ProductSummary(p.Id, p.Name, p.Price))
        .Take(limit)
        .ToListAsync();
```

## 5. Write calls

| 8.x | 9.0 |
|---|---|
| `RestoreById(id, ignoreQueryFilters: ...)` | `RestoreById(id, includeDeleted: ...)` |
| `RestoreByIdAsync(id, ignoreQueryFilters: ...)` | `RestoreByIdAsync(id, includeDeleted: ...)` |
| `HardDeleteById(id, ignoreQueryFilters: ...)` | `HardDeleteById(id, includeDeleted: ...)` |
| `HardDeleteByIdAsync(id, ignoreQueryFilters: ...)` | `HardDeleteByIdAsync(id, includeDeleted: ...)` |

The defaults are unchanged: `RestoreById` finds deleted entities by default, and `HardDeleteById` does not.

## 6. Source generator

| 8.x | 9.0 |
|---|---|
| `[GenerateUnitOfWork(typeof(AppDbContext))]` | Unchanged |
| `GenerateUnitOfWorkAttribute.DbContextTypes` | `GenerateUnitOfWorkAttribute.Sources` |
| `[GenerateUnitOfWork(dbContextTypes: ...)]` | `[GenerateUnitOfWork(sources: ...)]` |

The generator now also accepts entity types, for providers without a `DbContext`: `[GenerateUnitOfWork(typeof(Product), typeof(Order))]`. See [the source generator guide](../RapidRepo.SourceGenerators/unit-of-work.md).

The generated code is the same as in 8.x, except that it now adds `using System;` when a key type such as `Guid` needs it. The generated code therefore also compiles in projects without implicit usings.

## 7. Behaviour changes

| Area | 8.x | 9.0 |
|---|---|---|
| Paging without a sort order | Pages in whatever order the database returns | Orders by `Id`, so pages are stable on every provider |
| Editing or deleting an entity that is already soft-deleted | `DeletedAt` and `DeletedBy` were overwritten on every save | They are stamped only when the entity becomes deleted; `Delete` of a deleted entity keeps them |
| Deletion timestamp | `Delete` set `DeletedAt` immediately, then the commit overwrote it | Stamped at commit, like every other audit field |
| Adding and soft-deleting an entity in one commit | Inserted with the `Delete` call's time and no `DeletedBy` | Inserted as deleted, with the commit's time and user in `DeletedAt` and `DeletedBy` |
| Audit clock | `DateTime.UtcNow` | `TimeProvider`, `TimeProvider.System` by default; pass one to `EfUnitOfWork` to control it in tests |
| `IncludeDeleted` with `AddSoftDeleteQueryFilters()` | Bypassed every query filter | Bypasses only the soft-delete filter; other named filters, such as a tenant filter, stay in force |
| `IncludeDeleted` on an entity with only named filters that are not soft delete, or no soft delete at all | Bypassed every query filter | Bypasses nothing: there is no soft-delete filter to bypass, so a tenant filter stays in force |
| `AddSoftDeleteQueryFilters()` on a deletable type whose hierarchy root is not deletable | Threw from EF Core (a filter on a derived type) | Throws `InvalidOperationException` naming the type and its root. Implement `IDeletableEntity` on the root |
| `AddRapidRepo` without a provider | Warned only about a missing `DbContext` | Warns (through `Trace`) whenever it registers repositories or units of work, since nothing registers their data source |
| `AddSoftDeleteQueryFilters()` | Anonymous filter on every deletable entity type | Named filter `RapidRepo.SoftDelete`, registered on root entity types only. An entity with its own anonymous filter keeps the 8.x behaviour |
| `DeleteById` lookup | `DbContext.Find`, which also returned soft-deleted entities that were already tracked | The same lookup as the other by-id writes: unsaved additions whose key is already final, then a filtered query. `DeleteById(default)` no longer reaches an addition still waiting for a database-generated key |
| Overriding write methods of `EfRepository` | An override of `Delete`, `HardDelete`, `HardDeleteRange` or `Restore` saw direct calls only | It also sees the calls the write rules make, for example `DeleteById` → `Delete` → `HardDelete` |
| `UseUnitOfWork<TInterface, TImpl>()` with an abstract `TImpl` | Failed when the unit of work was first resolved | Throws `ArgumentException` at registration, like `UseUnitOfWork<TImpl>()` |
| `Any` / `AnyAsync` | No options | Accept `ReadOptions`, for example to include deleted rows |
| Unit of work disposal | Disposed the `DbContext` | Leaves the `DbContext` to its owner |
| `RegisterGenericRepositories` without a provider | Registered EF's `Repository<,>` | Throws with a message pointing at `UseEntityFrameworkCore()` |

### Soft-delete filters and tenant isolation

If your `DbContext` combines soft delete and tenant isolation in one hand-written filter, split it into named filters so that `IncludeDeleted` can bypass soft delete alone:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.AddSoftDeleteQueryFilters();                        // named "RapidRepo.SoftDelete"
    modelBuilder.Entity<Invoice>().HasQueryFilter("Tenant", i => i.TenantId == _tenantId);
}
```

EF Core does not allow anonymous and named filters on the same entity type. An entity that keeps a single anonymous filter still works, but for it `IncludeDeleted` bypasses every filter, as in 8.x.

## Upgrade checklist

1. Add `RapidRepo.EntityFrameworkCore`.
2. Replace `UseDbContext<T>()` with `UseEntityFrameworkCore<T>()`, and add `UseEntityFrameworkCore()` to `AddRapidRepo` calls that had no context.
3. Build. Fix the read calls that pass `orderBy` / `include` / `track` / `useSplitQueries` / `ignoreQueryFilters`, the `RestoreById` / `HardDeleteById` named arguments (sync and async), and the mock setups in your tests.
4. Optionally rename the `RRMIG001` types to their `Ef*` names, and remove `IDisposable` from unit of work interfaces.
5. Review paging calls without a sort order, and any code that relied on `DeletedAt` being re-stamped.
